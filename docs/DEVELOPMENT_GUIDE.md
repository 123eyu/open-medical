# 开发指南：面向医生的界面与交互

本指南约束 Open Medical 的产品设计、前端实现和相关业务交互。目标是让医生准确找到信息、核对依据、完成工作，并在中断后继续操作。视觉风格服务于这些任务。

开发环境见 [桌面版说明](DESKTOP.md)，数据与执行机制见 [架构说明](ARCHITECTURE.md)，完整使用流程见 [医生使用指南](DOCTOR_WORKBENCH_GUIDE.md)。

## 1. 使用方式与证据边界

规则分为三个层级：

- **必须**：本项目对新增和修改功能的验收要求。来自安全、可访问性或业务约束的项目决策，不表示每条都是法规原文。
- **默认**：无相反任务证据时采用的设计参数。调整时记录场景、理由和验证结果。
- **待验证**：需要目标医生实际使用后确认的假设，不得写成已证实的群体偏好。

本指南不是现有功能全部达标的声明。修改涉及的流程必须按对应规则检查；发现已有缺口时，记录影响、复现方式和改进项，不能用文档代替修复或验收。

研究核查日期：**2026-10-28**。这是围绕本项目问题的定向证据梳理，不是系统综述，也没有开展本项目的医生访谈或临床效果试验。参考文献覆盖 EHR、临床决策支持及可访问性；大型医院系统的结论迁移到个人桌面工作台时，需要重新验证。SAFER 是医疗信息系统安全实践参考，WCAG 是可访问性标准；引用它们不代表本项目获得认证或完成全面符合性评估。

优先级为：**患者和数据正确性 → 任务完成与可恢复性 → 可读性和操作效率 → 视觉一致性与审美偏好**。不能用更短的操作时间抵消错患者、错单位或漏掉异常等严重错误。

## 2. 研究能支持什么

| 证据 | 可以用于本项目的判断 | 不应据此外推 |
| --- | --- | --- |
| [R1：NIST 健康 IT 界面设计技术报告](#r1)，2015 | 从真实用户、任务、环境和使用风险出发，设计后进行任务验证 | 不是某种配色、圆角或布局的临床效果证明 |
| [R2–R4：2025 SAFER 指南](#r2) | 患者识别、可操作的风险提醒、检验与沟通后续处理需要完整流程 | 个人工作台不能仅靠界面获得医院级闭环管理能力 |
| [R5：WCAG 2.2](#r5) | 对比度、键盘、焦点、缩放和操作目标可以形成可测试要求 | 达到部分条款不等于整体 AA 合规，更不等于临床安全 |
| [R6：25 名美国 ICU 医师的定性研究](#r6)，2021 | 找到高优先级信息和处理信息过载，是具体界面问题 | ICU 的优先级和屏幕偏好不能直接代表中国门诊医生 |
| [R7：中国 6 家农村诊所、22 名临床人员的观察与访谈](#r7)，2021 | 本地工作流程、技术条件、透明度与信任影响 AI 工具使用 | 不能代表所有科室、医院层级或所有中国医生 |
| [R8：300 名社区医疗服务提供者的联合分析](#r8)，2023 | 被试对设备、色彩与布局有偏好，值得让真实用户比较方案 | “医疗服务提供者”不能直接等同于纯医生样本；不能推出“医生都喜欢绿色”“应只用图标”或“桌面应改为手机布局” |
| [R9：38 名住院医师及专科培训医师的模拟实验](#r9)，2019 | 异常检验纵向追踪改进，与该任务表现和部分负荷指标改善相关 | 整体自报负荷及耗时未显著改善；单中心模拟任务不能证明本产品降低医疗差错 |
| [R10：564 名医生的问卷研究](#r10)，2026 | 评估应同时考虑数据可用性、系统可用性、信息过载与认知负荷 | 横断面关联不能证明某次视觉改版的因果效果 |
| [R11：50 名医生的诊断推理随机试验](#r11)，2024 | 该研究中提供 LLM 并未显著改善医生诊断推理表现；必须验证人机协作流程 | 模型单独得分高，不等于医生使用后效果更好 |
| [R12：50 名医生的胸痛视频情境研究](#r12)，2025 | 接受 AI 建议后任务得分改善，提示收益可能依赖任务及呈现方式 | 随机分配的是患者人口学情境，AI 效果主要来自前后比较；不能视为所有任务上的 AI/无 AI 平行对照证据 |

据此，本项目采用“清楚、稳定、可核对、可恢复”的设计方向。下面的具体组件规则是结合研究和现有架构制定的工程要求，不是上述论文对 Open Medical 的直接验证结果。

## 3. 按工作情境理解医生

不得仅凭职业、年龄、性别或职称推断审美与数字能力。调研至少记录科室、诊疗场景、使用频率、设备与输入方式、资料来源、协作角色、系统熟悉程度，以及字号和可访问性需求。

以下是招募和设计时使用的**情境假设**，需通过观察修正：

| 情境 | 需要验证的主要任务 | 设计起点 |
| --- | --- | --- |
| 门诊接诊、患者之间快速切换 | 确认患者、查看近期变化、录入并保存 | 稳定的身份区、短路径操作、可恢复草稿 |
| 慢病复诊、长期管理 | 对照不同日期的用药、检验与随访 | 日期和单位同屏、纵向比较、未处理事项可见 |
| 资料整理、病案复核 | 定位原文、核对 AI 提取内容和矛盾 | 摘要与来源联动、逐项复核、保留冲突 |
| 文献学习、知识检索 | 判断来源、版本与适用范围 | 阅读宽度、准确引用、明确检索范围 |
| 初次使用或低频使用 | 理解术语、知道下一步、从失败中恢复 | 文字标签、就地帮助、有原因和下一步的状态反馈 |
| 熟练高频使用 | 连续输入、快速检索、减少重复操作 | 键盘路径、稳定位置、可记忆的个人偏好 |

同一名医生可能在一天内切换多种情境。允许调整字号、信息密度和栏目优先级，但患者身份、数据状态及必要风险信息不能因个性化而消失。

## 4. 设计与交互规则

### UX-01 患者身份与任务范围必须明确

- 患者页面、复核弹层及提交区域必须能核对当前患者。默认使用姓名和稳定患者编号；出生日期等已有可靠字段可辅助核对，不得为了补齐界面猜测身份信息。同名提示不能只靠头像或颜色。[R2](#r2)
- 患者、就诊/时间范围、当前任务必须分别表达。切换页面不能悄悄扩大检索或修改范围。
- 异步请求必须绑定患者及任务标识；患者 A 的迟到响应不得填入患者 B 的页面或草稿。提交前由服务端再次验证归属和版本。
- 切换患者时，未保存内容必须明确保留、保存或放弃；不得自动移交给下一位患者。导出前也须核对归属。

### UX-02 数据状态、时间与来源属于正文

- **无记录、未采集、未加载、加载失败、未检索到、明确阴性/正常**必须区分。没有过敏记录不能呈现为“无过敏”；空检验列表不能呈现为“指标正常”。
- 区分事件发生时间、报告时间、导入时间与摘要生成时间。临床排序不得无说明地用导入时间替代事件时间；未知日期显示未知。
- 汇总内容必须说明覆盖范围。仅检索部分资料时，不得写“已全面排查”；被筛选或截断的结果须显示范围及查看完整结果的入口。
- 关键事实要能回到原始资料的对应位置。引用需关联来源版本；来源修改、失效或不可访问时明确提示，不能只保留看似有效的链接。
- 多来源矛盾保留并列事实与出处，不得用“最新导入”自动消除冲突。摘要不能覆盖原始记录。

这些要求将数据可用性与界面可用性一起评估，避免只优化表面整洁。[R6](#r6) [R10](#r10)

### UX-03 用药与检验必须支持准确比较

- 药名、剂量、单位、频次、给药途径及使用状态按已有数据清楚呈现；未知项明确标识，不自动补全。当前用药、历史用药、停用和 AI 建议不得混为同一列表状态。
- 数值与单位紧邻；零值必须保留。参考范围优先使用对应报告及其适用条件，不能由前端配色逻辑创造医学阈值。
- 不同单位、项目定义或检测条件不得无校验地合并成趋势。单位转换须有确定性规则并保留原值；日期不明或同日冲突不能伪造成连续变化。
- 关键药名、剂量、异常值不能只用省略号隐藏。窄屏优先换行；确需二维比较的表格可局部滚动，并保留表头与行标识。
- 趋势图注明时间范围、单位、缺测点和坐标含义，并提供可读数值；不得靠平滑曲线、自动归零或夸张坐标制造未经证实的趋势。

纵向追踪应围绕实际识别与处理异常的任务验证。[R9](#r9)

### UX-04 信息密度由任务决定

- 默认提供“关键情况 → 需要处理的事项 → 相关明细 → 原始资料”的阅读路径。首屏排序依据当前任务，不按数据库表或后台模块顺序堆积。
- 同一判断所需信息尽量邻近，例如检验值、日期、单位与参考范围；不能要求医生在多个标签间记忆并拼接。
- 任务、知识和记录等重复条目默认用对齐的行或列表；有独立语义的摘要区域才使用卡片。避免每个字段一张卡、强制等高和无内容的大留白。
- 次要历史和低频配置可以渐进展开；不得为“极简”隐藏当前风险、来源缺口或未完成状态。折叠区应显示内容类别和必要数量。
- 新数据到达时不得自动重排正在点击的行、抢焦点或跳动阅读位置。默认提示有更新，由用户刷新或在安全时机应用。

“紧凑一定更快”和“留白越多越专业”都属于待验证假设。信息完整性、错误率与定位效率优先于截图观感。[R1](#r1) [R6](#r6)

### UX-05 视觉层级与文字必须可读

以下是**项目默认值**，不是医生群体审美的科学常数：

| 项目 | 默认要求 | 实现入口 |
| --- | --- | --- |
| 色彩 | 浅中性底色、深色正文、克制的绿色主操作；危险/警示色保留语义 | `src/style.css` 的设计令牌 |
| 标准字号 | 正文 16px，长文阅读 18px，辅助信息 14px | `src/business-layout.css` |
| 大字与特大字 | 复用现有字号模式；当前正文为 20px / 23px，阅读为 22px / 25px | `.large-text`、`.xlarge-text` |
| 布局 | 桌面允许相邻比较区域，空间不足转单列；避免固定高度裁切正文 | 页面组件及其样式 |
| 文案 | 标题用业务术语，按钮用“动词 + 对象”，状态说明实际发生的事 | 组件与共享显示模型 |

- 必须复用全局令牌和字号变量。不得在后加载样式中再次声明同名全局令牌，或用大量局部浅灰色覆盖统一对比度。
- 普通文字对比度至少 **4.5:1**；达到 WCAG 大文本条件时至少 **3:1**。大文本约为 24 CSS px 常规字或 18.7 CSS px 粗体；18px 正文不能自动按大文本计算。数据、日期、单位和来源也属于需要阅读的内容。[R5a](#r5a)
- 正常、选中、悬停、焦点、错误等状态都要检查；必要控件边界与状态标识遵循非文本对比要求，不能只测主按钮。[R5](#r5)
- 不能仅以红/绿、位置或图标传递含义；配合“待复核”“偏高”“已停用”等文字。临床异常、系统故障和普通进度要分清。
- 长中文标题、英文药名、连续数字、混合单位及大字号必须实测。避免把视觉弱化等同于降低文字可读性。
- 按钮不能只写“处理”“确定”；使用“保存记录”“确认应用修改”等可预期动作。`revision`、工具名、token 等实现细节放入可展开诊断信息。

### UX-06 键盘、缩放与操作目标必须可用

- 所有核心流程可用键盘完成；交互使用语义化控件，提供可访问名称。弹窗正确管理焦点、允许退出并将焦点返回触发处，不形成键盘陷阱。
- 焦点必须清楚可见，不能被固定栏完全遮挡。表单有持久标签；错误关联到字段，不能只在短暂 toast 中出现。[R5](#r5)
- 指针目标按 WCAG 2.2 AA 的 **24 × 24 CSS px 或符合条款的间距/其他例外**检查。主要操作默认采用至少 44px 高度及足够宽度；44px 是本项目操作便利性选择，不能误写为 AA 的统一最低尺寸。[R5c](#r5c)
- 检查文本放大 200% 后内容和功能不丢失；检查 320 CSS px 等效宽度的重排。一般内容避免双向滚动，必须二维展示的数据表按条款例外局部处理；只测一个窄屏截图不构成缩放验收。[R5](#r5) [R5b](#r5b)
- 保存、失败和完成状态应通过合适的状态语义通知辅助技术，不能把每个流式 token 都播报。重要结果保留可再次查看的入口。
- 默认不用自动播放、闪烁和装饰性循环动画；动效不阻碍连续操作，遵循减少动态效果偏好。

### UX-07 提醒必须分级、可解释、可处理

- 普通状态就地显示；需要关注的事项使用可见提醒；只有经业务与临床依据确认、需要即时决策的风险才打断流程。不得把所有异常都做成模态弹窗。[R3](#r3)
- 提醒至少说明对象、触发事实、时间/来源、待执行动作。提供直达相关资料或处理位置的入口，不能要求医生自行找回上下文。
- 风险级别由可审查的业务规则与临床依据确定，不能从 AI 语气、红色程度或任意阈值推断。缺少依据时显示“需要核对”，不伪装为已确诊风险。
- 区分已查看、暂缓、忽略、已处理与风险解除。关闭提示不能改变临床事实；重复提示的重新触发应有新证据或明确规则。
- 验证提醒命中、误报、重复出现和被忽略的原因。不能仅以“点击接受率高”证明安全，也不能只为减少弹窗而屏蔽重要信息。

### UX-08 AI 结果必须支持有效复核

- 明确区分原始记录、确定性计算结果、AI 草稿和医生确认内容。AI 输出不得借“已完成”状态伪装为已经核实的临床事实。
- 涉及业务写入的 AI 建议继续走类型化提案、差异预览、医生确认和确定性服务校验。复核时展示将修改的对象、字段、原值/新值及相关依据，不能只给一个“全部接受”。
- 核对重点包括患者、日期、药名、剂量与单位、否定词、过敏、异常值、遗漏和相互矛盾的资料。引用存在不代表引用能支持结论，必须能够查看原文。
- 显示实际使用的资料范围和无法完成的部分。没有校准和验证的模型自评百分比不得称为诊断概率或可靠度；推理文字也不能充当证据。
- 医生可以修改、拒绝、回到资料核对，并在 AI 不可用时继续基本记录和检索。确认控件不能默认选中，也不能把普通浏览变成反复审批。
- 复核结果须绑定提案版本和患者版本。原始数据已变化时提示重新核对，不能继续应用过时结论；重试不能重复写入。

复核界面本身需要测试。仅增加“请医生确认”文案，并不能证明能够避免错误采纳；验证应包含识别错误建议和保留正确建议两方面。[R7](#r7) [R11](#r11) [R12](#r12)

### UX-09 中断、延迟与失败必须可恢复

- 草稿、筛选条件和阅读位置在合理范围内保留，恢复时继续绑定原患者/任务。关键操作提供明确的保存中、已保存或未保存状态。
- 请求失败后保留输入并说明可执行的下一步；重试、取消、返回不能造成重复提交、静默丢失或错误患者归属。
- 运行状态区分排队、运行、等待复核、等待输入、失败、中断、取消和完成；用户离开页面不等于任务取消，生成结束也不等于业务已写入。
- 不伪造进度百分比或“马上完成”。只有实际进度可度量时才显示百分比；否则显示当前阶段和可执行动作。
- 不在后台刷新时清空整页、遮住已可读内容或抢占输入焦点。加载占位不得呈现虚构的正常结果。

### UX-10 随访与沟通必须表达真实闭环

- 区分计划已创建、提醒已触发、内容已起草、发送已请求、渠道已接收、对方已读、已回复及随访完成。渠道不提供的状态不能推测。
- 检验“已查看”与“后续行动完成”分开记录。需要跟进的事项保留负责人/处理人、到期时间、下一步与结果；单人工作台也要能找到未完成项。[R4](#r4)
- 发送前可核对患者、接收者、渠道和最终内容，沿用已有授权机制；自动化任务显示实际授权范围，不把草稿误报为发送成功。
- 失败、超时、无法联系和无回复必须有明确状态。关闭提醒、归档对话或 AI 声称完成，不能直接完成随访。

### UX-11 个人偏好与信息边界必须透明

- 字号、密度和栏目偏好应可恢复默认，并与临床事实分离；不得因为用户隐藏栏目而修改患者数据。
- 个性化默认保留稳定导航和关键操作位置。新增功能不能突然重排已熟悉的主流程；明显改变时提供必要的迁移说明。
- 外发、导出、复制和分享应让用户知道对象与资料范围，使用已有授权和权限校验。不能以“本地应用”为由声称数据永不外发。
- 演示、截图、测试夹具和问题反馈使用合成或适当脱敏的数据；错误日志不得包含密钥或无关患者正文。真实资料的查看权限不能自动扩大为可公开分享。

### UX-12 每次改动都必须有任务证据

- 开始前写清“谁、在什么情境、要完成什么、当前哪里受阻”，并选择对应规则与验收任务。
- 先复用现有组件、显示模型和业务服务。不得为视觉改版新增无用途的状态、临床规则、模型调用或整套 UI 框架。
- UI 不复制医学判断和写入校验。数字格式、状态文案和临床数据语义尽量放在共享显示模型；业务写入由服务层执行。
- 验收覆盖操作后的真实结果，而非只看按钮反馈或截图。代码检查通过、页面好看、医生任务表现改善必须分别描述。

## 6. 验收方法

### 6.1 与改动相关的最小任务集

使用隔离的合成数据，从真实入口执行完整流程。按改动选择相关任务；修改全局样式、患者上下文、状态机或共享显示模型时，扩大覆盖到受影响页面。

| 验收任务 | 必须检查的结果 | 规则 |
| --- | --- | --- |
| 打开同名患者 A，发起读取后切换 B，再等待 A 返回 | 身份正确；旧结果不串入；草稿保持归属 | UX-01、09 |
| 阅读缺日期、缺单位、零值、明确阴性和读取失败的资料 | 缺失与正常分开；零值保留；错误不伪装为空数据 | UX-02、03 |
| 对照跨日期检验和在用/停用药物 | 单位、时间、状态可核对；冲突不被自动合并 | UX-03、04 |
| 从概览发现一条待处理事项，查看依据并处理 | 来源可到达；处理记录与提示状态一致；未处理项可找回 | UX-02、07、10 |
| 复核一份含遗漏、错误剂量或错误引用的合成 AI 草稿 | 可发现并修改/拒绝；不直接写入；不会重复提交 | UX-08 |
| 修改提案所依据的数据后再确认原提案 | 版本冲突得到解释；过时提案不能覆盖新数据 | UX-01、08 |
| 填写一半后切页、模拟断网/服务错误，再恢复 | 输入保留；状态真实；重试结果可核验 | UX-09 |
| 起草并模拟发送随访消息、模拟失败与无回执 | 草稿、渠道回执和实际随访结果不混淆 | UX-10 |
| 键盘完成核心流程，切换大字号并放大/缩窄窗口 | 焦点可见且顺序合理；必要内容不裁切；局部表格可用 | UX-05、06 |

代码改动运行 `npm run check`，再执行与变更风险对应的现有测试及交互检查。纯文档改动检查文件链接、规则一致性和引用即可。不要用只重复实现细节的测试代替上述任务验证。

### 6.2 医生参与的验证

内部浏览器测试只能证明操作和数据行为，不能代替真实医生对内容优先级和工作负担的判断。

1. **先观察任务。** 让目标医生回顾一次具体接诊、复诊、资料核对或学习过程，记录信息来源、切换、中断和重复录入；不要只问喜欢哪个颜色。
2. **按情境招募。** 早期可先邀请 6–8 名覆盖主要使用情境的医生探索问题。这是项目规划起点，不是统计学充分样本，也不是“发现全部问题”的保证；差异大的科室和角色分别验证。
3. **比较同一任务。** 旧版与候选版使用等难度合成病例、相同设备和资料，平衡呈现顺序；将首次学习与熟练操作分别记录，减少学习效应。
4. **分别度量。** 首先看患者/数据错误、遗漏与独立完成情况；再看耗时、定位次数、返回查找、恢复中断的难度。满意度、可读性、审美评价分别记录，不能合成一个“更好看所以更好用”的结论。
5. **验证 AI 的正确依赖。** 同时放入正确建议、错误建议和依据不足的建议，观察是否会核对、合理采纳或拒绝。仅统计采纳率不能评价协作质量。
6. **留下可追溯记录。** 记录版本、参与者情境、任务、预设成功条件、实际结果、问题严重性与修正项。不得把小样本偏好写成“医生普遍喜欢”。

可使用 SUS 等可用性量表或 NASA-TLX 等负担量表辅助比较，但不能把量表分数当作临床安全证明。若需要声称统计显著改善或临床效果，应另行设计相应研究，预先确定指标、样本量与分析方案。

发现错患者、静默丢数据、错误剂量/单位转换、未经确认写入等严重问题时，该流程不得按通过交付。其他指标在测试前设定相对当前版本的目标，不能看完结果再更换标准。一次测试未发生严重错误，也不等于证明风险为零。

### 6.3 变更说明应回答的问题

- 改善了哪项医生任务，涉及哪些 UX 规则？
- 哪些内容有外部证据，哪些只是本项目选择或待验证假设？
- 检查了哪些正常、缺失、冲突、失败和中断场景，结果如何？
- 有哪些尚未实现或未经医生验证的限制？

## 7. 仍需验证的设计假设

| 假设 | 验证方式 | 不满足时的调整方向 |
| --- | --- | --- |
| 浅中性背景与绿色主操作适合主要用户 | 在相同内容和对比度下比较阅读与主观评价 | 改主题参数，不改变警示语义 |
| 当前 16px 正文及字号模式覆盖主要需求 | 长时间阅读、大字号、缩放与真实设备观察 | 调整字号和行距，保留个人选择 |
| 桌面双列概览有利于复诊核对 | 比较单列/双列的定位、遗漏和滚动情况 | 按任务或窗口调整布局 |
| 默认栏目顺序适合主要科室 | 不同科室完成相同类型任务并指出信息缺口 | 调整默认或提供有限配置 |
| 紧凑列表减少查找成本 | 比较不同密度下的定位时间与误点击 | 改行距及分组，不删关键字段 |
| 现有 AI 复核能帮助发现错误 | 使用含可控错误的草稿进行任务测试 | 改差异与来源呈现，减少无效确认 |

在新科室、新设备、主要流程变化或新证据出现时重新评估。不能用一次审美投票锁死后续设计。
